# 十分钟入门异步编程 —— 结合 ChatServer 项目

> 读完这篇文章，你将理解：事件循环怎么跑、回调何时触发、对象生命周期如何管理、多线程安全怎么保证。

---

## 第 1 分钟：同步 vs 异步 —— 一句话理解

```
同步：你打电话订餐，电话接通后你啥也不能干，等对方说完才能挂。
异步：你发微信订餐，消息发完你就能去干别的事，回复到了手机会响铃通知你。
```

| | 同步 (sync) | 异步 (async) |
|---|---|---|
| 当前线程 | 阻塞等待，啥也不干 | 立即返回，继续执行 |
| 结果通知 | 函数返回值 | 回调函数 / future |
| CPU 利用 | 低（干等） | 高（等待期间处理别的请求） |
| 代码复杂度 | 简单，从上到下 | 回调嵌套，需要管理生命周期 |

**你项目的本质**：一台服务器要同时处理成百上千个客户端。如果用同步，一个客户端卡住，所有人排队——服务器瘫痪。用异步，一个线程就能同时"照看"所有连接。

## 第 2 分钟：事件循环（io_context）—— 异步的心脏

项目代码入口 `chatserver.cpp`:

```cpp
boost::asio::io_context io_context;   // ← 这就是事件循环引擎
```

**io_context 就像一个快递分拣中心**：

```
                  ┌─────────────────────────┐
                  │      io_context          │
                  │  (事件循环 / 快递中心)     │
                  │                          │
   async_accept ──▶  ① 新连接到达  ──▶ 回调 HandleAccept
   async_read   ──▶  ② 数据到达    ──▶ 回调 on_read
   async_wait   ──▶  ③ 定时器到期  ──▶ 回调 on_timer
   async_write  ──▶  ④ 发送完成    ──▶ 回调 on_write
                  │                          │
                  │  .run() 不停地轮询这些事件 │
                  └─────────────────────────┘
```

**关键认知**：`io_context.run()` 是一个死循环，不断地从队列中取事件、执行对应的回调。所有你在项目中注册的 `async_xxx` 操作，最终都由 `.run()` 来驱动：

```cpp
// AsioIOServicePool.cpp —— 每个线程都在跑 .run()
for (std::size_t i = 0; i < _ioServices.size(); ++i) {
    _threads.emplace_back([this, i]() {
        _ioServices[i].run();   // ← 事件循环主循环，阻塞在这里
    });
}
```

## 第 3 分钟：async_accept —— 非阻塞地接客

[CServer.cpp](CServer.cpp#L19-L23) `StartAccept()`:

```cpp
void CServer::StartAccept() {
    auto& io_context = AsioIOServicePool::GetInstance()->GetIOService();
    std::shared_ptr<CSession> new_session = std::make_shared<CSession>(io_context, this);
    _acceptor.async_accept(
        new_session->GetSocket(),
        std::bind(&CServer::HandleAccept, this, new_session, std::placeholders::_1)
    );
}
```

**执行流程**：

```
StartAccept() 调用 async_accept
        │
        │  注册事件："当有新连接到达时，调用 HandleAccept"
        │  然后立即返回 ← 不阻塞！
        ▼
  io_context.run() 继续处理其他事件
        │
        │  ... 可能过了 3 秒 ...
        │
        ▼
  新客户端连接到端口
        │
        ▼
  io_context 触发回调 → HandleAccept(new_session, error_code)
        │
        ├─ new_session->Start()      // 开始读取这个客户端的数据
        ├─ _sessions.insert(...)     // 登记到在线表
        └─ StartAccept()             // 再次调用，继续监听下一个连接
```

**要点**：
- `async_accept` 只注册一个"意图"，不会阻塞等连接。
- 每次接收完一个连接，必须再次调用 `StartAccept()` 形成监听循环。
- 门卫服务器 `Cserver`（[gateserver 版本](d:\qtstudy\server\gateserver\GateServer\Cserver.cpp)）也是同样的模式。

## 第 4 分钟：回调 & 生命周期 —— 为什么 `this` 很危险

来看项目中两段代码的对比。

### ❌ 危险写法：捕获裸指针 `[this]`

```cpp
// CServer.cpp 第141行 —— on_timer 末尾的重置
_timer.async_wait([this](const boost::system::error_code& ec) {
    on_timer(ec);    // 如果 CServer 在此之前被销毁，this 是野指针 → 崩溃
});
```

**时序陷阱**：

```
T=0s:   async_wait 注册，60秒后回调
T=30s:  CServer 对象因故被销毁（服务器停止 / 异常）
T=60s:  定时器到期，io_context 调用回调
        → this 指向已释放的内存 → 未定义行为（崩溃/数据错乱）
```

### ✅ 安全写法：捕获 `shared_ptr`

```cpp
// CServer.cpp 第71行 —— StartTime()
auto self = shared_from_this();
_timer.async_wait([self](boost::system::error_code ec) {
    self->on_timer(ec);   // 安全！只要回调存在，对象就存在
});
```

**原理**：

```
                 ┌────────────────────────┐
                 │  shared_ptr<CServer>   │  引用计数 = 2
                 │  ├─ 外部持有者          │
                 │  └─ lambda 中的 self   │
                 └──────────┬─────────────┘
                            │
              外部释放 → 引用计数 -1 = 1
              对象还活着！
                            │
              lambda 执行完毕 → 引用计数 -1 = 0
              对象安全析构
```

**前提**：类必须继承 `enable_shared_from_this`，对象必须由 `shared_ptr` 管理：

```cpp
// CServer.h 第9行
class CServer : public std::enable_shared_from_this<CServer> {
    // ...
};
```

## 第 5 分钟：完整的异步读取链 —— async_read → callback → async_write

[HttpConnection.cpp](d:\qtstudy\server\gateserver\GateServer\HttpConnection.cpp#L132-L157) `Start()`:

```cpp
void HttpConnection::Start() {
    auto self = shared_from_this();                              // ① 保活
    http::async_read(_socket, _buffer, _request, [self](        // ② 注册异步读
        beast::error_code ec, std::size_t bytes_transferred)
    {
        if (ec) {
            std::cout << "http read err is " << ec.what() << std::endl;
            return;
        }
        self->HandleRequest();                                   // ③ 解析 HTTP 请求
        self->CheckDeadline();                                   // ④ 启动超时定时器
    });
}
```

```
    async_read("等客户端发数据")
         │
         │  立即返回，线程继续处理别的请求
         │
         ▼
    数据到达 → 回调被触发
         │
         ├─ HandleRequest()  解析 GET/POST，处理逻辑
         │      │
         │      └─ WriteResponse()  → async_write("把响应发回去")
         │             │
         │             └─ [self](...) { _socket.shutdown(...); }
         │
         └─ CheckDeadline()  如果60秒内没完成 → 强制关闭 socket
```

**整个链路没有一次阻塞**。`async_read` → `HandleRequest` → `async_write` 形成了异步处理流水线。

## 第 6 分钟：定时器 heartbeat —— 用 `async_wait` 做周期任务

[CServer.cpp](CServer.cpp#L78-L145) `on_timer()` —— 你问过的这段代码：

```cpp
void CServer::on_timer(const boost::system::error_code& ec) {
    // ---------- 第1步：错误检查 ----------
    if (ec) {
        // 定时器被取消（如服务器关闭），直接返回
        std::cout << "timer error: " << ec.message() << std::endl;
        return;
    }

    // ---------- 第2步：拷贝 session 表后释放锁 ----------
    std::map<std::string, std::shared_ptr<CSession>> sessions_copy;
    {
        std::lock_guard<std::mutex> lock(_mutex);
        sessions_copy = _sessions;
    }  // ← 锁在这里就释放了！遍历用的是副本

    // ---------- 第3步：遍历副本，检测心跳 ----------
    const std::time_t now = std::time(nullptr);
    for (const auto& [session_id, session] : sessions_copy) {
        if (session->IsHeartbeatExpired(now)) {
            session->Close();                       // 关闭TCP → 触发 async_read 错误回调
            expired_sessions.push_back(session);    // 收集起来，稍后处理
            continue;
        }
        ++session_count;                            // 存活的才计数
    }

    // ---------- 第4步：上报在线人数到 Redis ----------
    RedisMgr::GetInstance()->HSet(LOGIN_COUNT, self_name, std::to_string(session_count));

    // ---------- 第5步：处理过期 session（不持锁！防止死锁） ----------
    for (auto& session : expired_sessions) {
        session->DealExceptionSession();  // 这里会获取 _mutex 从 _sessions 中移除
    }

    // ---------- 第6步：重置定时器，形成循环 ----------
    _timer.expires_after(std::chrono::seconds(60));
    _timer.async_wait([this](const boost::system::error_code& ec) {
        on_timer(ec);
    });
}
```

**这个函数包含了你项目中最精华的三个设计模式**：

### 模式 1：拷贝-释放-遍历（Copy-Release-Iterate）

```
┌──────────────────────────────────────────────┐
│  错误做法（长时间持锁）                         │
│                                              │
│  lock(_mutex);                               │
│  for (auto& s : _sessions) {                 │
│      s->Close();  ← 可能阻塞                 │
│      s->DealExceptionSession(); ← 需要获取_mutex │
│  }                                           │
│  unlock(_mutex);                             │
│  → 锁持有时间长 + 可能死锁                     │
└──────────────────────────────────────────────┘

┌──────────────────────────────────────────────┐
│  正确做法（你的代码）                           │
│                                              │
│  { lock(_mutex); copy = _sessions; } ← 瞬锁   │
│  for (auto& s : copy) { s->Close(); }        │
│  for (auto& s : expired) { s->Deal...(); }   │
│  → 锁持有时间极短 + 遍历不持锁 + 无死锁风险     │
└──────────────────────────────────────────────┘
```

### 模式 2：分离副作用（Separate Side Effects）

第3步只做**判断和收集**，第5步才做**清理**。因为 `DealExceptionSession()` 内部会调用 `ClearSession()`，而 `ClearSession()` 需要获取 `_mutex`。如果在前面的循环里直接调用，就会形成：

```
持锁遍历 → 内部需要锁 → 死锁！
```

### 模式 3：自循环定时器（Self-Rescheduling Timer）

```cpp
_timer.expires_after(std::chrono::seconds(60));   // 设置"从现在起60秒后"
_timer.async_wait([](ec) { on_timer(ec); });      // 注册下一次
```

这是一个**永不停止的循环**，每60秒执行一次。相比 `while(true) + sleep(60)`，它不占用线程。

## 第 7 分钟：多线程 —— IO Context Pool

[AsioIOServicePool.cpp](AsioIOServicePool.cpp):

```cpp
AsioIOServicePool::AsioIOServicePool(std::size_t size)
    : _ioServices(size), _works(size), _nextIOService(0)
{
    // 每个 io_context 配一个 work —— 防止 .run() 没有任务时退出
    for (std::size_t i = 0; i < size; i++) {
        _works[i] = std::unique_ptr<Work>(new Work(_ioServices[i]));
    }
    // 每个 io_context 分配一个线程去跑
    for (std::size_t i = 0; i < _ioServices.size(); ++i) {
        _threads.emplace_back([this, i]() {
            _ioServices[i].run();   // ← 每个线程都在自己的事件循环中
        });
    }
}

// 轮询分配——新连接到来时，选一个 io_context 来处理
boost::asio::io_context& AsioIOServicePool::GetIOService() {
    auto& service = _ioServices[_nextIOService++];
    if (_nextIOService == _ioServices.size()) {
        _nextIOService = 0;   // 轮转回来
    }
    return service;
}
```

**架构图**：

```
                    新连接到来
                        │
              GetIOService() 轮询分配
                        │
         ┌──────────────┼──────────────┬──────────────┐
         ▼              ▼              ▼              ▼
    ┌─────────┐   ┌─────────┐   ┌─────────┐   ┌─────────┐
    │ io_ctx0 │   │ io_ctx1 │   │ io_ctx2 │   │ io_ctx3 │
    │ .run()  │   │ .run()  │   │ .run()  │   │ .run()  │
    │         │   │         │   │         │   │         │
    │ thread0 │   │ thread1 │   │ thread2 │   │ thread3 │
    └─────────┘   └─────────┘   └─────────┘   └─────────┘
        │              │              │              │
    处理连接A      处理连接B      处理连接C      处理连接D
```

**为什么每个 io_context 需要一个 `work`？**

`io_context.run()` 的行为是：**当没有待处理任务时，立即返回（退出）**。`work` 是一个"占位符"，它告诉 io_context："我还有活要干，别退出"。直到调用 `stop()` + `work.reset()`，`run()` 才会退出。

```cpp
void AsioIOServicePool::stop() {
    for (auto& work : _works) {
        work->get_io_context().stop();  // 停止 io_context
        work.reset();                    // 释放 work，让 run() 能够返回
    }
    for (auto& thread : _threads) {
        thread.join();                   // 等待所有线程退出
    }
}
```

## 第 8 分钟：线程安全 —— mutex、condition_variable、atomic

### mutex——保护共享数据

```cpp
// CServer.h
std::map<std::string, std::shared_ptr<CSession>> _sessions;
std::mutex _mutex;
```

`_sessions` 这个 map 会被多个线程同时访问：主线程接受新连接要插入，定时器线程要遍历，session 关闭要删除。**任何读写都必须持锁**：

```cpp
// 读操作
std::shared_ptr<CSession> CServer::GetSession(std::string session_id) {
    std::lock_guard<std::mutex> lock(_mutex);
    auto it = _sessions.find(session_id);
    // ...
}

// 写操作
void CServer::ClearSession(std::string session_id) {
    std::lock_guard<std::mutex> lock(_mutex);
    _sessions.erase(session_id);
}
```

### condition_variable——生产者-消费者

[VerifyGrpcClient.h](d:\qtstudy\server\gateserver\GateServer\VerifyGrpcClient.h) 的连接池：

```cpp
std::unique_ptr<VarifyService::Stub> GetCon() {
    std::unique_lock<std::mutex> lock(mutex_);
    cond_.wait(lock, [this] {
        if (b_stop_) return true;
        return !connections.empty();     // 队列不空才继续
    });
    // 取出一个连接
    auto context = std::move(connections.front());
    connections.pop();
    return context;
}

void returnCon(std::unique_ptr<VarifyService::Stub> context) {
    std::lock_guard<std::mutex> lock(mutex_);
    connections.push(std::move(context));
    cond_.notify_one();   // 通知等待者："有货了！"
}
```

**工作流程**：

```
  线程A: GetCon()              线程B: returnCon()
      │                              │
      ├─ 队列空 → cond_.wait()       │
      │  (线程A 阻塞等待)    ────────→ ├─ 用完归还到队列
      │                              ├─ cond_.notify_one()
      ├─ 被唤醒 ←───────────────────   │
      ├─ 取走一个连接                  │
      └─ 继续执行                    └─ 继续执行
```

### atomic——无锁的布尔开关

```cpp
std::atomic<bool> b_stop_;    // 比 bool + mutex 更轻量
```

`atomic` 保证读写的原子性，适合简单的开关标志位。

## 第 9 分钟：gRPC 同步调用的异步化

[VerifyGrpcClient.h](d:\qtstudy\server\gateserver\GateServer\VerifyGrpcClient.h) 中的 gRPC 调用本身是**同步**（阻塞）的：

```cpp
GetVarifyRsp GetVarifyCode(std::string email) {
    ClientContext context;
    GetVarifyRsp reply;
    GetVarifyReq request;
    request.set_email(email);

    // 设置 30 秒超时 —— 防止阻塞过久
    context.set_deadline(
        std::chrono::system_clock::now() + std::chrono::seconds(30));

    auto stub = pool_->GetCon();    // 从连接池取
    Status status = stub->GetVarifyCode(&context, request, &reply);
    // ↑ 这里会阻塞，等待 gRPC 服务端返回
    pool_->returnCon(std::move(stub));  // 归还到连接池
    return reply;
}
```

**为什么不直接用异步 gRPC？** —— 同步代码更简单。这个阻塞调用发生在 GateServer 自己的线程中，不会阻塞主事件循环。通过**连接池** + **超时设置**来控制风险。

**分层架构**：

```
客户端 (Qt) ──TCP──▶ GateServer (异步 HTTP/Beast) ──gRPC──▶ VerifyServer
                         │                                      │
                    io_context.run()              独立线程处理 gRPC 调用
                    非阻塞处理 HTTP                同步阻塞 gRPC（可接受）
```

## 第 10 分钟：完整链路走通一遍

结合你的全部项目代码，看一个客户端请求的完整生命周期：

```
1. 客户端发起 TCP 连接
        │
        ▼
2. CServer::StartAccept()
   └─ _acceptor.async_accept(...)   ← 注册异步接受
        │
        ▼  连接到达
3. HandleAccept()
   ├─ new_session->Start()        ← 注册 async_read
   ├─ _sessions.insert(...)       ← 登记在线
   └─ StartAccept()               ← 继续监听下一个
        │
        ▼  客户端发来数据
4. CSession::on_read()  回调触发
   ├─ 解析协议（HTTP 请求 / 自定义协议）
   ├─ 业务处理（验证码 / 登录 / 聊天消息）
   ├─ 可能需要调用 gRPC（到 VerifyServer 验证）
   └─ async_write(response)      ← 异步发送响应
        │
        ▼  发送完成
5. on_write() 回调触发
   └─ 再次 async_read(...)        ← 继续读下一条消息
        │
        │  ... 同时，定时器线程在后台运行 ...
        │
        ▼  每60秒
6. CServer::on_timer()
   ├─ 拷贝 _sessions
   ├─ 检查心跳
   ├─ 关闭超时的 → 触发 async_read 错误回调 → 清理 session
   └─ 上报人数到 Redis
        │
        ▼  服务器关闭
7. AsioIOServicePool::stop()
   ├─ work.reset()                ← 释放 work
   ├─ io_context.stop()           ← 停止事件循环
   └─ thread.join()               ← 等待线程退出
```

**这一切，几十个线程就撑起了成百上千的并发连接。**

## 常见坑 & 最佳实践

### 1. 回调中 `[this]` vs `[self]`

```cpp
// ❌ 危险：对象可能已被销毁
_timer.async_wait([this](auto ec) { this->on_timer(ec); });

// ✅ 安全：shared_ptr 保证对象存活
auto self = shared_from_this();
_timer.async_wait([self](auto ec) { self->on_timer(ec); });
```

### 2. 不要在持锁时调用可能再次获取锁的函数

```cpp
// ❌ 死锁风险
{
    lock_guard<mutex> lock(_mutex);
    for (auto& s : _sessions) {
        s->Cleanup();  // Cleanup 内部需要 _mutex → 死锁
    }
}

// ✅ 拷贝后释放锁再处理
std::map<...> copy;
{
    lock_guard<mutex> lock(_mutex);
    copy = _sessions;
}
for (auto& s : copy) { s->Cleanup(); }
```

### 3. 每个 async 操作都要处理 error_code

```cpp
// ❌ 忽略错误
_timer.async_wait([self](auto ec) { self->on_timer(); });

// ✅ 先检查错误
void on_timer(const boost::system::error_code& ec) {
    if (ec) {
        std::cout << "timer error: " << ec.message() << std::endl;
        return;  // 定时器被取消，不要继续
    }
    // ... 正常逻辑
}
```

### 4. 异步链中不要忘记下一次注册

```cpp
void HandleAccept(...) {
    new_session->Start();       // 读数据
    _sessions.insert(...);      // 登记
    StartAccept();              // ← 必须再次调用！否则不再接受新连接
}
```
